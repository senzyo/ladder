## 第二轮已确认的决策

- 保留单一 Cargo crate 和全局状态机制，在 crate 内按职责拆模块，不改成全面依赖注入架构。
- 优先验证并使用当前版本 `windows` 依赖的类型化 COM 接口，替代手写 vtable 和 `PROPVARIANT` 布局。允许为此开启必要 features；不为 COM 迁移升级 `windows` 版本。前置依赖维护范围另见交接文档。切换门槛为双架构编译与 amd64 原生 COM/通知验证通过，并对比发布产物体积；ARM64 原生验证单列，缺少环境时明确标为未验证，不以交叉构建替代。
- 统一内部术语：`Core` 为代理核心身份、`CoreSettings` 为核心设置、`CoreStatus` 为安装及运行状态、`ConfigSelection` 为配置选择。领域定义见根目录 `GLOSSARY.md`。
- 将格式化行宽从 120 调整到 100，改名和格式化分批执行，避免混入语义调整。
- 本方案继续采用 Rust stable；不为自动导入整理等选项强制切换 nightly。

## 第三轮已确认的决策

### 按资源处理中毒锁

| 资源 | 新策略 | 保留的边界 |
| --- | --- | --- |
| 全局应用状态 | 不读取中毒数据，释放错误携带的锁守卫，进入紧急清理并以失败状态退出 | 未初始化仍按现有调用方的分支处理，不能和中毒混为一谈 |
| 文件日志 | `write`、`flush` 返回固定 IO 错误，不再使用文件内容或调用 tracing | 独立 stderr 日志层继续尝试输出；release 没有控制台时不保证可见 |
| 启动警告缓存 | 不读取旧队列，返回固定的“启动警告缓存不可用”消息 | 不因警告重放失败阻止启动；配置加载的默认值和纠正策略不变 |

不得使用 `PoisonError::into_inner()` 或 `clear_poison()` 绕过问题，也不能统一改成 `expect()`。

### 紧急清理与 panic

- 状态中毒时使用集中紧急终止入口，不能依赖普通 panic 间接进入清理。
- 普通 panic 钩子也使用同一套清理底层函数：不获取应用状态锁，不通过 tracing 写日志，不弹 Toast 或 MessageBox。
- 现有进程枚举、终止、DNS 恢复、DNS 刷新函数内部也有日志。必须核查整个调用链，不能只删除钩子首行日志。
- 普通操作的包装函数继续保留现有日志；紧急路径直接调用不写 tracing 的底层函数。避免通过临时替换 tracing dispatcher 来宣称安全。
- 清理顺序保持为尝试停止核心、恢复 DHCP DNS、刷新 DNS。普通 panic 在清理尝试结束后仍调用原默认钩子输出诊断。
- 保留 release 的 `panic = "abort"`；不能依赖 Drop 或展开执行关键清理。
- 不承诺清理必然成功：系统调用失败、并发活动、再次 panic、内存不足或系统直接终止均可能打断清理。此次不扩大为核心进程生命周期或 DNS 策略重设计。

决策背景见 [ADR 0001](../adr/0001-poison-and-emergency-cleanup.md)。

### 全局状态通过闭包访问

- 使用 `with_app_state` 和 `with_mut_app_state`，分别传入共享引用和可变引用；闭包采用 `FnOnce`，支持移入或取出子进程句柄。
- 不向其他模块返回 `MutexGuard`，也不能让状态借用逃出闭包。
- 保留当前锁范围的语义：获取快照后再枚举进程、显示菜单、下载或终止核心。
- **保存设置是明确的现有例外**：核心模式修改、规则集更新时间修改及对应 `settings.save()` 仍在同一次可变访问中串行执行。不得拿旧设置快照到锁外保存。
- 保存失败时内存已经改变，这是现有行为，不新增回滚。原本在该锁范围内的失败日志/通知也先保持；缩短其锁范围属于另一次并发行为调整。
- 下载完成后重新访问当前状态，只更新仍存在的规则集条目，不能把下载前的整份设置写回。
- 闭包内部不得嵌套获取同一状态锁；闭包中的 `return` 不能导致外层任务误报成功。
- 忙标志守卫覆盖完整后台操作，不随状态访问闭包结束而释放。

## 已知不变量

- 主线程与通过 `spawn_bg` 启动的菜单后台线程各自初始化 COM；不扩大到规则集或 stderr 转发等其他线程。
- 单实例互斥体跨会话生效；创建失败时允许启动。
- panic 清理路径不获取全局应用状态锁；保留 release 的 `panic = "abort"`。
- 退出时先终止核心并恢复 DNS，再销毁窗口。
- 后台任务完成、提前返回及线程创建失败时均释放忙标志。
- 终止进程和下载等耗时操作不持有应用状态锁。
- 日志上限允许最后一次写入跨过阈值，只追加一次上限通知；0 表示不限量。
- 保留发行目录、配置菜单按文件名去重、更新文件白名单与失败回滚语义。
- 保留更新下载失败已通知后返回成功的现有调用契约，避免重复通知或阻断另一个核心的更新。
- 保留版本比较对缺失、无效及溢出段的容错，不替换成严格 semver 解析。
- 保留配置键结构、默认值、边界修正、警告和稳定序列化顺序。

## 已确认规则的落地方式

- 入口只保留模块声明及少量装配；日志、命令分发和 Windows 生命周期移入对应叶模块。
- 保留现有 `AppError`，不为风格整改新增错误框架。
- 用具名内部结构表达 release 信息、下载资产和配置解析结果；配置文件及远端 JSON 的格式保持不变。
- 将仅在单个函数使用的 trait 局部导入；普通跨模块函数保留模块限定；类型通过显式导入使用。
- 为必须检查的返回值和资源守卫审查 `#[must_use]`，已有 `Result` 等类型保证的地方不重复标注。
- 将返回 `Result` 的 `ComGuard::new` 改为 `try_new`；能直接 derive 的 `Default` 不再手写。
- 将 `unsafe` 缩小到 FFI 操作，说明必要性并补齐 `SAFETY:`；需要调用方保证条件的接口保留 `unsafe` 和明确安全契约。
- 对资源释放和所有权调整逐项核查：若会顺带修复独立缺陷，则将该修改排除出本轮，不能以 RAII 重构名义混入。
- 对内联测试保留规范允许的 `use super::*`；测试中的 `catch_unwind` 改用隔离线程等方式验证展开释放，不全局替换 panic 钩子。
- 不对本应用内部类型机械添加面向跨团队公共 API 的 `#[non_exhaustive]`，不套用 Chromium/Fuchsia 专属要求。

完整逐条审查见 [规范对照清单](google-rust-style-checklist.md)。其中“已满足”代表当前静态初审结论，实施结束还需复核。

| `src/core.rs` | `Core` 及紧密相关的文件清单、状态类型等核心元数据，不访问全局状态 |
| `src/config_selection.rs` | `ConfigSelection` 和候选配置发现、排序、去重 |

原 `state.rs` 的职责迁移完毕后不再保留空壳。只删除迁移后的重复实现，不删除功能。`build.rs` 仅进行适用的导入、命名和不变量说明调整，忽略复制错误等既有契约保持。

不同时让一个模块负责声明业务子模块又承载大量实现；需要进一步拆分时优先增加根声明的叶模块，避免把原根模块问题转移到新的父模块。

## 类型化 COM 的实施约束

**2026-10-24 执行决策：本节接口迁移暂缓。** windows 0.62.2 的公开 typed 方法把所有非负 HRESULT 转为成功，无法保留现有 `hr != 0` 失败判定；生成 vtable 又属于隐藏 API。用户已选择保持现有错误判定，保留这段手写接口，不为此次迁移增加 features。以下约束保留为将来恢复该项时的要求，不能将延期标为验证通过。

仅开启现有 `windows` 依赖需要的 features：`Win32_UI_Shell_PropertiesSystem`、`Win32_System_Com_StructuredStorage`、`Win32_System_Variant`。其他位置仍需要的 `windows-sys` 保留，不以统一依赖为目标。

- 使用公开的 `IPropertyStore`、`SHGetPropertyStoreFromParsingName` 和 `PROPVARIANT` 绑定，删除被替代的手写 vtable、GUID 绑定和偏移写入；属性键的实际值保持。
- 当前属性值为 `VT_LPWSTR`，借用一个有效的、以空字符结尾的 UTF-16 缓冲区。不得直接用会生成 `VT_BSTR` 的字符串转换替换它。
- 当前 typed `PROPVARIANT` 的 Drop 会清理内部资源。保留借用指针时，应在最小局部范围使用 `ManuallyDrop` 等明确的借用适配，保证缓冲区覆盖整个调用期；绝不能把 `Vec` 的内存交给 COM 释放。
- typed `IPropertyStore` 接管接口释放后，删除对应手工 Release，确保只释放一次。
- AUMID、属性类型与键、快捷方式位置、COM 初始化线程、保存/提交顺序、错误判定和通知回退不变；专门核对 HRESULT 到 `Result` 的成功/失败映射。
- 如果验证发现某个绑定不能保持既有契约，停止该项迁移，记录具体差异并重新讨论，不默认扩大行为修改范围。
- 不设未经确认的产物增长阈值；以同工具链、同配置的双架构前后体积报告作为审查证据。

## 分批实施顺序

以下为前置依赖维护验收后的重构批次，不代表自动提交 Git。先完成交接文档中的 S0、D1–D4，并将其验证结果作为重构基线；本节的基线步骤复用这些证据，仅在代码、工具链或环境变化时补跑必要检查。

1. **建立基线**：记录工具链、依赖锁和工作区状态；运行现有格式、Clippy、测试及双架构构建，记录测试数量与 release 字节数。构建脚本会复制配置和资源，基线使用独立目标目录，不启动实际应用。
2. **格式与机械命名**：先单独调整 100 列格式；再单独完成已确认类型名、`try_new`、缩写、导入和 `expect` 上下文。每批保留可独立审阅的差异。
3. **职责迁移**：按模块映射移动代码与原测试，修正调用路径；先保持原锁与错误语义，确认迁移没有功能变化。
4. **内部 API 对齐**：引入具名结果、闭包状态访问、必要的 `must_use` 和 derive；处理迭代链、断言及文档；把展开释放测试改为隔离线程验证，保留原覆盖目的。
5. **故障策略**：按已确认方案替换全部中毒内部值恢复；接入不经过 tracing 的紧急清理，并用隔离测试验证退出、降级和钩子调用链。
6. **Windows 边界**：在已有依赖上验证 typed COM，再收缩各 FFI 边界并补齐安全说明。已知图标泄漏等独立缺陷不夹带处理。
7. **最终验收**：复核规范清单和所有行为不变量，完成自动检查、双架构构建和可用环境中的 Windows 验证；逐项报告未验证部分与独立缺陷。

## 验收条件

### 自动检查

- `cargo fmt --check`
- `cargo clippy --all-targets --locked -- -D warnings`
- `cargo test --locked`
- `cargo build --release --locked`
- 在已准备 ARM64 MSVC 交叉编译环境中运行 `cargo build --release --locked --target aarch64-pc-windows-msvc`，并检查对应目标。
- 使用独立 `CARGO_TARGET_DIR`，避免构建脚本覆盖开发者现有运行目录的设置；不更改全局工具链或环境配置。
- 现有 58 个测试的覆盖目的不得丢失；测试数量因迁移/拆分可变化，验收不只看数量。
- 新增有意义的测试限于改动风险：资产 URL/hash 字段映射、设置解析结果、状态闭包与串行保存、中毒处理和紧急路径。用固定样本、局部对象、临时目录及测试替身，不依赖真实下载。

### 故障测试隔离

- 通过独立工作线程持有局部 `Mutex` 后 panic 来制造中毒，不毒化静态应用状态，不在普通并行测试中替换全局 panic 钩子。
- 日志测试验证文件停止写入、另一输出层仍收到事件，并且不会递归记录日志。
- 警告缓存测试验证不会读取中毒旧数据，仍能返回固定降级提示。
- 退出和 panic 钩子测试在独立子进程中进行，注入只记录步骤的清理替身；父进程设置超时、检查步骤及退出结果。
- 测试替身绝不能调用真实 DNS、注册表改写、计划任务注册或代理进程终止入口；这些测试不证明操作系统清理必然成功。

### Windows 与发布证据

- 使用临时目录验证快捷方式的 AUMID 值、属性类型、提交/读取及错误分支；实际 Toast 验证单列记录。
- amd64 原生 COM/通知验证与双架构编译是 typed COM 切换的必过项；arm64 交叉构建仅证明编译链接，原生运行验证需要 ARM64 环境，缺少时单列未验证。
- 记录两架构 release 大小的改前/改后字节数及百分比，不使用旧注释中的历史体积替代基线。
- 托盘菜单、模式切换、配置选择、正常退出和 DNS 恢复的实际验证在可恢复的隔离环境安排；实施阶段若无此环境，明确列为未验证，不为通过验收擅自在用户日常网络环境执行。
- 普通 PR CI 未执行双架构 release 构建，不能以其通过替代上述构建证据。暂不改变 CI 的触发或发布逻辑。
- 验收报告必须区分自动检查通过、Windows 实际验证通过、尚缺运行环境三种状态；未满足的项不得标为通过。

## 独立缺陷清单

- `src/tray.rs` 的 `load_icon_bitmap` 在 `CreateDIBSection` 失败分支释放内存 DC 和图标，但遗漏释放此前取得的屏幕 DC。按已确认范围独立处理。
- `src/tray.rs` 从文件加载的应用图标未见对应释放；共享图标与自有图标需区分生命周期。单列核查及修复，不能统一无条件销毁。
- `src/tray.rs` 的消息循环通过 `GetMessageW(...).as_bool()` 判断结果，未单独处理 -1 错误；是否在现有调用条件下实际触发尚未证明。
- `src/scheduler.rs` 写入临时 XML 后，启动 `schtasks` 失败会绕过删除步骤。
- `src/toast.rs` 将图标路径放入 XML 属性时未转义，包含 `&` 等字符的路径需要独立回归用例。
- `src/process.rs` 修改 TUN 配置时使用字符串定位，目标 inbound 与被改字段的位置可能不一致；应另行验证压缩 JSON 及多个同名字段的案例。
- 以上清单只记录发现，不构成本轮修复授权。
